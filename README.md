# Kaspi POS Automation

Автоматизация платежей для POS-систем через Kaspi Pay API. Проект предоставляет серверное приложение и веб-интерфейс для создания счетов, генерации QR-кодов, просмотра истории транзакций и оформления возвратов.

## Архитектура

```
┌──────────────┐       ┌──────────────────┐       ┌──────────────────┐
│  Web UI      │◄─────►│  Express Server   │◄─────►│  Kaspi Pay API   │
│  (public/)   │       │  (server.js)      │       │  (entrance/      │
│              │       │                   │       │   mtoken/qrpay)  │
└──────────────┘       └──────────────────┘       └──────────────────┘
                              │
                    ┌─────────┴─────────┐
                    │   src/            │
                    │  ├─ config.js     │  Keypair, device, constants
                    │  ├─ crypto.js     │  ECDH, ECDSA, TOTP, AES
                    │  ├─ helpers.js    │  Fetch wrapper, headers
                    │  ├─ session.js    │  Stateless session factory
                    │  ├─ logger.js     │  File & console logging
                    │  ├─ polling.js    │  Payment status polling
                    │  ├─ webhookStore  │  Webhook management
                    │  └─ routes/       │  API route handlers
                    │     ├─ auth.js    │  SMS auth (3-step)
                    │     ├─ invoice.js │  Invoice creation
                    │     ├─ qr.js      │  QR code generation
                    │     ├─ history.js │  Transaction history
                    │     ├─ refund.js  │  Refund processing
                    │     └─ session.js │  Session management
                    └───────────────────┘
```

Один сервер обслуживает несколько проектов, у каждого — **свой счёт Kaspi Pay**, банковская сессия,
ключи устройства, журнал и вебхуки. API-ключ проекта автоматически выбирает его счёт. Администратор
выполняет SMS-вход отдельно для каждого проекта; банковские токены проектам не передаются.

### Webhooks

Сервер автоматически отслеживает статусы созданных QR- и invoice-платежей (polling каждые 3 сек.) и отправляет HTTP POST-уведомления на указанные URL при изменении статуса.

- 📡 **События:** `payment.success` · `payment.failed` · `payment.expired` · `payment.lost`
- ⚙️ **Настройка проектов и вебхуков:** встроенная админка, данные в SQLite.
- `webhooks.json` сохраняется только для legacy-платежей.
- 🔐 **Подпись:** HMAC SHA-256
- 🔄 **Retry:** до 3 попыток с нарастающей задержкой

> 📖 Подробнее — в [документации API](./docs/API.md#webhooks).

## Требования

- Docker Engine + Docker Compose ≥ 2.24 для контейнерного запуска; либо Node.js ≥ 24 для локального запуска.

## Запуск через Docker

Для новой установки `.env` не обязателен:

```bash
docker compose up -d --build
docker compose logs kaspi
```

В логах найдите `[ADMIN SETUP]`: логин `admin` и уникальный временный пароль. Их можно посмотреть
через Logs в Portainer, без SSH. Откройте админку по HTTPS-домену, войдите и задайте постоянный
пароль (12–128 символов). До смены временного пароля управление проектами недоступно.
Временный пароль повторяется в логах при перезапуске до первой смены; затем его копия удаляется.

Сервер сам создаёт постоянный ключ шифрования в `DATA_DIR/server-secrets.json` и административный
API-ключ в SQLite. Ключ шифрования не показывается в интерфейсе и не меняется обычным редактированием.
Административный API-ключ можно посмотреть или перевыпустить в «Настройках сервера» после ввода
текущего пароля. Вход по паролю и API-ключ независимы: ротация ключа не завершает браузерную сессию.

**При обновлении существующей установки сохраните прежний `.env` и volume.** Старый `TOKEN_SECRET_KEY`
проверяется на существующей базе и только после этого сохраняется в защищённый файл. Если ключа нет,
а база или банковские данные уже существуют, сервер остановится и попросит восстановить прежний ключ.
Новый ключ вместо старого автоматически не создаётся.
Старый `ADMIN_API_KEY` остаётся рабочим; после явного перевыпуска в интерфейсе прежнее значение ENV
перестаёт участвовать в авторизации и не восстановит старый ключ при перезапуске.

Для необязательных настроек `APP_*`, `PORT` и первоначальных ключей можно использовать `.env.example`.
Необязательный `env_file` требует Docker Compose ≥ 2.24 ([Docker Docs](https://docs.docker.com/compose/how-tos/environment-variables/set-environment-variables/)).

Контейнер работает от пользователя `node`, автоматически перезапускается и проверяет `/health`.
Порт публикуется на `127.0.0.1:3000`; для доступа через интернет настройте HTTPS reverse proxy.
`PORT` в `.env` меняет внешний порт; внутренний — `3000`.

`projects.json` и переменные API-ключей проектов для новой установки не нужны. SQLite создаётся
автоматически в `DATA_DIR/projects.sqlite` внутри volume `kaspi-data`.

## Управление через админку

1. Откройте `/`, введите логин `admin` и свой пароль. При первом входе смените временный пароль из логов.
2. Создайте проект: укажите название, при необходимости задайте постоянный ID.
3. Сохраните выданный API-ключ. Администратор может повторно открыть его кнопкой «Показать API-ключ» в карточке или настройках проекта.
4. Нажмите «Подключить счёт Kaspi Pay» в карточке или настройках проекта. В модальном окне введите номер кассира и SMS-код. Для уже подключённого счёта доступно открытие и повторное подключение.
5. В настройках проекта добавьте URL вебхуков и события. Секрет нового вебхука можно задать вручную
   или получить автоматически; автоматически созданный секрет показывается один раз.

В админке можно менять название, вебхуки и их секреты, отключать проект, перевыпускать API-ключ и
удалять проект. Изменения сразу используются API и polling — SSH и перезапуск контейнера не нужны.
Авторизация проверяет SHA-256-хеш API-ключа. Для повторного просмотра администратором дополнительно хранится копия ключа, зашифрованная AES-256-GCM; секреты вебхуков также зашифрованы. Список проектов не содержит ключей или зашифрованных значений.
Банковские токены проектам не выдаются.

Кнопка «Доставка вебхуков» открывает журнал с фильтрами, поиском и пагинацией: видны получатель,
платёж/заказ, статус доставки, HTTP-код, ошибки и история попыток. После успешной доставки или трёх
ошибок записи сохраняются в SQLite. Администратор может повторно поставить уведомление в очередь;
исходный `X-Webhook-ID` сохраняется для защиты сайта от дублирования обработки.
«Доставлено» подтверждает HTTP 2xx от сайта, а обновление заказа проверяется на стороне сайта.
Старые удалённые доставки восстановить нельзя; ожидающие мигрируют автоматически.

Кнопка «Платежи» в админке или карточке проекта открывает локальный журнал: QR и счета, сумма, номер
заказа, дата создания, результат и исходный статус Kaspi. Доступны выбор проекта (включая архивные),
поиск по началу ID/заказа, фильтр статуса и страницы по 50 записей. Поиск, фильтрация и пагинация выполняются в SQLite на сервере; браузер получает только выбранную страницу. Список обновляется каждые 10 секунд;
это чтение последнего состояния фонового отслеживания, а не отдельный запрос статуса каждого платежа к банку.
«Требует сверки» не означает отказ оплаты: сервер не смог подтвердить результат.
Журнал содержит только платежи, созданные через этот сервер; полная банковская история открывается в рабочем пространстве счёта.

Для ключей, созданных старой версией SQLite-хранилища и сохранённых только как хеш, просмотр недоступен:
исходное значение восстановить нельзя. Такой ключ продолжает работать. При необходимости администратор
явно перевыпускает его и обновляет настройки сайта; автоматически ключ не меняется. Новые ключи и ключи,
импортированные из JSON с исходным значением, можно просматривать повторно.

«Секрет проверки уведомлений» нужен вашему сайту, чтобы проверить, что уведомление об оплате отправил
именно этот сервер. Это не пароль Kaspi и не API-ключ проекта. Для нового вебхука поле можно оставить
пустым: сервер создаст секрет автоматически. У существующего вебхука пустое поле сохраняет текущий секрет.

Удаление **архивирует** проект и отзывает его API-ключ. История и банковские данные сохраняются,
уже созданные платежи продолжают отслеживаться и отправлять уведомления. Отключение проекта также
останавливает приём новых запросов по его ключу, но сохраняет текущие платежи.
ID остаётся постоянным и не может быть назначен другому проекту после архивирования.

Список показывает наличие сохранённой банковской сессии, организацию и время последней проверки.
Проверка сессии/подключение подтверждает её через Kaspi; само наличие сохранённой сессии не гарантирует,
что банк всё ещё принимает её. При вытеснении сессии потребуется повторный SMS-вход.

## API проектов

Все `/api/*` требуют `Authorization: Bearer <API_KEY>`. Ключ проекта автоматически выбирает его счёт.
Чужие платежи недоступны для просмотра, отмены и возврата. Администратор выбирает счёт заголовком
`X-Project-ID`; управление `/api/projects` не требует этого заголовка.

```bash
curl http://127.0.0.1:3000/api/qr/create \
  -H "Authorization: Bearer $PROJECT_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"amount":"1500.00","orderId":"order-123"}'
```

`PROJECT_API_KEY` в примере — ключ, выданный админкой, установленный в окружении вашей интеграции.
`orderId` служит для сопоставления заказа; он не обеспечивает идемпотентность создания платежа.
Суммы нормализуются единообразно: KZT, два знака, ROUND_HALF_UP (`1.005` → `1.01`).
Доступность возврата и остаток определяет Kaspi. Все маршруты — в [API](./docs/API.md).

## Хранение и обновление

Платежи, очередь доставки вебхуков и настройки проектов хранятся в одной базе
`DATA_DIR/projects.sqlite`. В Docker это `/app/data/projects.sqlite` в постоянном volume `kaspi-data`.
База использует WAL и индексы по проекту, результату, дате, ID и заказу. API возвращает только
нужную страницу; polling читает незавершённые платежи пакетами до 100 записей, очередь — только
уведомления с наступившим сроком отправки. Завершённая история не загружается в память.
Финальный статус и задания вебхуков фиксируются одной транзакцией. Данные сессии незавершённого
платежа зашифрованы AES-256-GCM и удаляются из его записи после завершения; API их не выдаёт.
Денежные суммы при миграции сохраняются без пересчёта, правило новых платежей — KZT, два знака, ROUND_HALF_UP.

При первом обновлении сервер автоматически импортирует `payments-state.json` из `DATA_DIR`.
Если его нет, импортируются прежние `tracked-payments.json` и `webhook-retries.json`.
Импорт платежей и очереди выполняется одной транзакцией с маркером завершения: прерванный импорт
откатывается и повторяется при следующем запуске. Ошибочный JSON останавливает запуск, не создавая
частичный журнал. После успешного импорта файлы остаются резервными копиями, больше не читаются
и не обновляются. Не запускайте старую версию сервера на этих копиях: они уже не отражают новые платежи.
Для первой миграции JSON разбирается в памяти один раз; дальнейшая работа использует только SQLite.

В volume сохраняются `projects.sqlite` (и файлы WAL/SHM), `server-secrets.json`, логи и отдельные каталоги
`projects/<id>/` с ключами устройств и банковскими сессиями.
На одном volume запускается один процесс приложения. Журнал платежей хранится без автоматического удаления.
Не удаляйте volume или `server-secrets.json` и не меняйте `TOKEN_SECRET_KEY` при обычном обновлении. Сохраняйте `.env` и
согласованную резервную копию volume; простой способ — копировать volume при остановленном контейнере.

Обновление кода: `docker compose up -d --build`. Изменения проектов через админку не требуют этой команды.
Смена настроек процесса в `.env` требует `docker compose up -d --force-recreate`.

## Миграция прежней конфигурации

При первом открытии новой базы сервер импортирует существующий `projects.json` и значения переменных
`*_API_KEY`/`*_WEBHOOK_SECRET`, на которые он ссылается. ID, API-ключи, банковские сессии и устройства
сохраняются. Импорт выполняется транзакционно, один раз; затем единственным источником настроек становится SQLite.
Ошибочная конфигурация прерывает импорт без частичного создания проектов. Старые файлы остаются на месте.

Для первого обновления Docker-установки сохраните старый `.env` с ключами проектов и используйте:

```bash
docker compose -f compose.yaml -f compose.import.yaml up -d --build
```

Этот дополнительный Compose-файл монтирует прежний `./projects.json` для первого импорта.
После успешного запуска используйте обычный `compose.yaml` и управляйте проектами через админку;
старые переменные проектов больше не участвуют в авторизации и доставке вебхуков. Если база уже существует,
изменения старого JSON/переменных не перезаписывают её содержимое.

Старые `tracked-payments.json` и `webhook-retries.json` импортируются в журнал с владельцем `__admin__`;
они не назначаются произвольному новому проекту. Legacy `webhooks.json` обслуживает только такие операции.

## Локальный запуск

Требуется Node.js ≥ 24 со встроенным `node:sqlite`. После настройки двух секретов в `.env`:

```bash
npm ci
npm start
```

По умолчанию рабочие данные хранятся в корне репозитория. Можно задать `DATA_DIR=./data`.

| Переменная         | Описание                                                                                         | По умолчанию                             |
| ------------------ | ------------------------------------------------------------------------------------------------ | ---------------------------------------- |
| `TOKEN_SECRET_KEY` | Прежний постоянный ключ AES-256-GCM, 64 hex-символа; для новой установки создаётся автоматически | —                                        |
| `ADMIN_API_KEY`    | Первоначальный ключ административного API; необязателен, генерируется автоматически              | —                                        |

| `DATA_DIR`         | Каталог SQLite и остальных постоянных данных                                                     | Корень репозитория; `/app/data` в Docker |
| `PROJECTS_FILE`    | Необязательный путь JSON для одноразовой миграции                                                | `./projects.json`, отсутствие допустимо  |

принимаемого банком клиента и пересоздайте контейнер. Для настроек проектов эта процедура не требуется.

## Доступ администратора

Браузер использует HttpOnly cookie сессии со сроком 12 часов; в production cookie требует HTTPS.
Сессии и ограничения попыток входа хранятся в SQLite. Пароль хранится как scrypt-хеш с уникальной солью.
Все изменяющие запросы браузера требуют `X-CSRF-Token`; Bearer API для интеграций сохраняется.
Смена пароля завершает остальные браузерные сессии, выход отзывает текущую сессию на сервере.
После пяти неудачных проверок пароля с одного адреса действует пауза до 15 минут.

Если пароль забыт, выполните в консоли контейнера (например, Portainer → Console):

```bash
npm run admin:reset-password
```

Либо с VPS: `docker compose exec kaspi npm run admin:reset-password`.
Команда выдаёт новый временный пароль, отзывает все браузерные сессии и требует сменить пароль при входе.
Ключи API и банковские сессии при этом сохраняются.

## Ротация ключей

```bash
# Локальный запуск
npm run regen:keypair -- <project-id>  # Перегенерация ECDSA-ключей проекта
npm run regen:device -- <project-id>   # Перегенерация идентификатора устройства проекта

# Docker
docker compose exec kaspi npm run regen:keypair -- <project-id>
docker compose exec kaspi npm run regen:device -- <project-id>
docker compose restart kaspi
```

После ротации перезапустите сервер и пройдите SMS-вход заново только для выбранного проекта.

## Демо-интерфейс (`public/`)

В папке `public/` находится встроенный веб-интерфейс (SPA), который запускается автоматически вместе с сервером и доступен по адресу `http://localhost:3000`.

**Возможности интерфейса:**

- 🔐 **Авторизация администратора** — «Войти в панель», затем «Подключить счёт Kaspi Pay» в карточке или настройках проекта. SMS-вход выполняется отдельно для каждого счёта; локальная сессия браузера ведётся отдельно для каждого проекта
- 🧾 **Выставление счёта** — создание счёта по номеру телефона клиента с указанием суммы и комментария
- 📱 **QR-оплата** — генерация QR-кода для оплаты с отслеживанием статуса в реальном времени
- 📋 **История операций** — просмотр списка транзакций с детализацией
- 💰 **Продажи и возвраты** — статистика продаж и оформление возвратов

**Файлы:**

| Файл                | Описание                                              |
| ------------------- | ----------------------------------------------------- |
| `public/index.html` | HTML-разметка и стили интерфейса                      |
| `public/app.js`     | Клиентская логика (API-вызовы, управление состоянием) |

> Интерфейс предназначен для демонстрации и тестирования API. Для продакшена рекомендуется использовать собственный фронтенд.

## Единый QR — приём платежей от других банков

При создании QR-кода через `/api/qr/create` в ответе возвращаются два поля:

- **`QrToken`** — ссылка вида `https://pay.kaspi.kz/pay/...`, работает только в приложении Kaspi.
- **`QrOriginalToken`** — оригинальная ссылка вида `https://qr.kaspi.kz/...`, поддерживает оплату через **Единый QR** (приложения других банков).

Чтобы клиенты могли оплачивать через приложения других банков, генерируйте QR-код из значения **`QrOriginalToken`**, а не из `QrToken`.
