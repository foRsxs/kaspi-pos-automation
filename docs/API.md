# API Kaspi POS Automation

Базовый URL локально: `http://127.0.0.1:3000`. Через интернет используйте HTTPS reverse proxy.
Один экземпляр обслуживает несколько проектов; у каждого — свой счёт и сессия Kaspi Pay.

## Доступ и сессия

Интеграции `/api/*` используют `Authorization: Bearer <API_KEY>`; отсутствующий или неверный ключ — `401`.
Браузерная админка использует HttpOnly cookie-сессию и `X-CSRF-Token` на изменяющих запросах;
API-ключ администратора в браузерном хранилище не сохраняется. `/api/admin/login` — вход по паролю.
API-ключ проекта автоматически выбирает его счёт; переданный клиентом `projectId` не меняет владельца операции.
Администратор передаёт `X-Project-ID: <id>` из SQLite / админки для запросов с выбранным проектом. Без заголовка
сервер отвечает `400`, с неизвестным ID — `404`. Если проектный ключ сопровождается чужим `X-Project-ID`,
сервер отвечает `403`. `/api/projects` — административное исключение: заголовок не нужен.
`X-Token-SN`, `X-Vtoken-Secret`, `X-Profile-ID` больше не используются. Для каждого проекта на сервере
отдельно хранятся ключи устройства и банковская сессия; её секрет зашифрован `TOKEN_SECRET_KEY`.
Проектам банковские токены не выдаются.

| Доступ                                  | Эндпоинты                                                                                                                    |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Без ключа                               | `GET /health` — `{ "status": "ok" }`                                                                                         |
| `ADMIN_API_KEY` или полная admin-сессия | `GET /api/projects` без `X-Project-ID`; `/api/auth/*`, `/api/session/*`, `/api/history/*`, `POST /api/invoice/history` с ним |
| Ключ проекта или администратор          | Создание QR/счёта, проверка статуса, отмена счёта, возврат, `GET /api/payments`; администратор указывает `X-Project-ID`      |

Проект может читать, отменять и возвращать только созданные им платежи. Чужой или неизвестный ID — `404`,
без запроса в Kaspi. Банковские ID должны содержать только цифры. Администратор работает со счётом,
выбранным через `X-Project-ID`; созданные им платежи принадлежат этому проекту. `GET /api/payments`
возвращает журнал проекта по Bearer-ключу либо выбранному администратором ID.

### Управление проектами — только администратор

Эти маршруты требуют `ADMIN_API_KEY` или полную браузерную сессию администратора и не требуют `X-Project-ID`. Изменения применяются сразу.
Ответы содержат `Cache-Control: no-store`; ключи и секреты не включаются в списки проектов.

| Метод и путь                        | Тело / параметры                      | Результат                                                                      |
| ----------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------ |
| `GET /api/projects`                 | Необязательно `?includeArchived=true` | `{projects: [...]}`                                                            |
| `GET /api/projects/:id/api-key`     | —                                     | `{apiKey}`; просмотр текущего ключа только администратором                     |
| `GET /api/projects/:id`             | —                                     | `{project}`; включая архив                                                     |
| `POST /api/projects`                | `{name, id?}`                         | `201 {project, apiKey}`; ключ доступен администратору для повторного просмотра |
| `PATCH /api/projects/:id`           | `{name?, status?, webhooks?}`         | `{project, webhookSecrets: [{id, secret}]}`                                    |
| `POST /api/projects/:id/rotate-key` | `{}`                                  | `{project, apiKey}`; прежний ключ сразу недействителен                         |
| `DELETE /api/projects/:id`          | —                                     | `{project}` со статусом `archived`; история сохраняется                        |

Публичные поля проекта: `id`, `name`, `status` (`active`, `disabled`, `archived`), `createdAt`, `updatedAt`, `canRevealApiKey`,
`webhooks` (`id`, `url`, `events`, `hasSecret`) и `connection` (`connected`, при наличии `orgName`,
`phone`, `profileId`, `verifiedAt`). `connected` отражает сохранённую сессию и известные серверу отказы;
живую проверку выполняет `/api/session/check`.

При создании ID можно не указывать — сервер сформирует постоянный идентификатор. Его изменение и повторное
использование после удаления запрещены. `status` через PATCH принимает `active` или `disabled`;
архивный проект нельзя включить обратно. API-ключ отключённого/архивного проекта получает `401`.
Администратору также запрещено создавать новые платежи для такого проекта.

`GET /api/projects/:id/api-key` возвращает текущий ключ без перевыпуска и изменения его действия.
Проектным ключам маршрут недоступен (`403`); без авторизации — `401`. Ответ не кэшируется (`Cache-Control: no-store`).
В списке и обычном ответе проекта по-прежнему нет plaintext, хеша или ciphertext ключа.
`canRevealApiKey` показывает наличие зашифрованной копии текущего ключа; у архивных проектов — `false`.
Старый ключ, сохранённый только как хеш, продолжает работать, но просмотр возвращает `409`:
`{ "code": "API_KEY_NOT_RECOVERABLE", "error": "..." }`. Автоматического перевыпуска нет.
Для восстановления возможности просмотра администратор явно перевыпускает ключ и обновляет интеграцию.
Архивирование отзывает ключ и удаляет его зашифрованную копию.

`webhooks`, если передан, заменяет весь набор получателей проекта. Для редактирования существующего
получателя передайте его `id`; отсутствие `secret` сохраняет текущий секрет. У нового получателя без
`secret` сервер сгенерирует его и вернёт только в `webhookSecrets` этого ответа. Можно задать свой секрет
не короче 32 печатных ASCII-символов. `webhooks: []` удаляет все подписки.

Пример создания:

```bash
curl http://127.0.0.1:3000/api/projects \
  -H "Authorization: Bearer $ADMIN_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"name":"Интернет-магазин","id":"shop"}'
```

Проект определяется своим Bearer-ключом. Администратор передаёт `X-Project-ID` для банковских маршрутов
и `/api/payments`. Отключение/архивирование сохраняет отслеживание существующих платежей и их вебхуки.
Архивные банковские данные остаются доступны администратору по ID для сверки истории и возвратов.

## Вход и настройки сервера

Новые установки автоматически создают ключ шифрования и административный API-ключ. Существующий
`TOKEN_SECRET_KEY` сохраняется; смена мастер-ключа через настройки не поддерживается, поскольку
требует отдельного перешифрования данных. `GET /api/admin/settings` возвращает только признак настройки и источник ключа.

| Метод и путь                     | JSON                                | Назначение                                                                                             |
| -------------------------------- | ----------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `POST /api/admin/login`          | `username`, `password`              | Вход, HttpOnly/SameSite=Strict cookie, `authenticated`, `username`, `mustChangePassword`, `csrfToken`  |
| `GET /api/admin/session`         | —                                   | Текущая сессия и CSRF-токен; без сессии `401`                                                          |
| `POST /api/admin/password`       | `currentPassword`, `newPassword`    | Пароль 12–128 символов, отзыв всех сессий и выдача новой текущей сессии                                |
| `POST /api/admin/logout`         | `{}`                                | Отзыв текущей сессии, `204`                                                                            |
| `GET /api/admin/settings`        | —                                   | Полная cookie-сессия; `username`, `encryptionKeyConfigured`, `encryptionKeySource`, `apiKeyConfigured` |
| `POST /api/admin/api-key/reveal` | `password`                          | Полная сессия и повторная проверка пароля; `{apiKey}`                                                  |
| `POST /api/admin/api-key/rotate` | `password`, необязательный `apiKey` | Заменить ключ; пустой или отсутствующий `apiKey` генерируется сервером; `{apiKey}`                     |

Все POST с cookie (кроме входа) требуют `X-CSRF-Token`; токен приходит при входе/чтении сессии.
Запросы с чужим `Origin` отклоняются. Пароли и API-ключи не передаются в URL.
До смены временного пароля доступны только сессия, смена пароля и выход; прочие браузерные запросы
возвращают `403` с `ADMIN_PASSWORD_CHANGE_REQUIRED`. Cookie действует 12 часов, в production имеет `Secure` и требует HTTPS.
После 5 неудачных проверок пароля с одного адреса возвращаются `429` и `Retry-After`.
Административные Bearer-запросы для прежних интеграций сохраняются и не требуют cookie/CSRF.
После ротации `ADMIN_API_KEY` в интерфейсе старый ENV-ключ не восстанавливается при перезапуске.
Все ответы `/api/admin/*` имеют `Cache-Control: no-store`.

## Подключение Kaspi Pay администратором

При первом запуске откройте `/`, введите логин `admin` и временный пароль из `[ADMIN SETUP]` в логах контейнера.
Задайте постоянный пароль, после чего откроется панель проектов. При следующих входах используется этот пароль.
В карточке или настройках нужного проекта нажмите «Подключить счёт Kaspi Pay», затем в модальном окне введите номер
кассира и SMS-код. Если счёт уже подключён, доступно открытие банковского рабочего пространства
и отдельное повторное подключение по SMS. Оно не удаляет действующую серверную сессию до успешного входа.
После подтверждения окно покажет результат: «Готово» возвращает к проектам или настройкам,
«Открыть счёт» открывает банковское рабочее пространство выбранного проекта.

Сессия администратора хранится в HttpOnly cookie, CSRF-токен — в памяти страницы. Локальный банковский контекст
ведётся отдельно для каждого проекта. Выход отзывает браузерную сессию на сервере; сохранённые
банковские сессии и приём платежей продолжают работать.

| Метод и путь                | JSON / параметры           | Ответ                                                                                                               |
| --------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `POST /api/auth/init`       | `{}`                       | `success`, `processId`, `view`, `body`                                                                              |
| `POST /api/auth/send-phone` | `processId`, `phoneNumber` | `success`, `desc`, `view`, `errorCode`, `errorMessage`, `body`                                                      |
| `POST /api/auth/verify-otp` | `processId`, `otp`         | При успехе: `success: true`, `step: "finished"`, `profileId`, `organizationId`, `orgName`, `phone`, `organizations` |
| `GET /api/session/check`    | —                          | `active: true`, `profileId`, `orgName`, `phone`; при неактивной сессии — `401`                                      |

Для всех перечисленных банковских маршрутов с `ADMIN_API_KEY` передавайте `X-Project-ID`; тогда SMS-поток
и сохранённая сессия относятся к выбранному счёту. Запросы с ключом проекта автоматически используют его счёт.

Пример первого шага:

```bash
curl -X POST http://127.0.0.1:3000/api/auth/init \
  -H "Authorization: Bearer $ADMIN_API_KEY" \
  -H 'X-Project-ID: shop' \
  -H 'Content-Type: application/json' -d '{}'
```

Номер кассира: 10 цифр без кода страны (`7001234567`); входящие 11 цифр с префиксом `7`/`8`
приводятся к 10 цифрам. SMS-процесс действует 10 минут. При вытеснении сессии входом на другом устройстве
администратор проходит SMS-вход снова для соответствующего проекта. Для разных счетов не нужны отдельные
экземпляры сервера. Удалённые устаревшие маршруты: `/api/auth/session`, `/api/auth/logout`.

## Создание и проверка платежей

Сумма передаётся числом или десятичной строкой. Единое правило для QR, счетов и возвратов:
**KZT, 2 знака, ROUND_HALF_UP** (`"1.005"` → `1.01`). После округления сумма должна быть положительной,
максимум `999999999999.99`. Отрицательные, `null`, экспоненциальные строки и нечисловые значения дают `400`.
Для точного десятичного ввода используйте строки.

При создании журнал сохраняет проверенную сумму запроса: `Data.Amount: 0` в ответе создания
не заменяет её нулём. При финализации корректная положительная `Data.Amount` из ответа статуса
обновляет сумму журнала и нового вебхука в одной транзакции. Нулевое, отсутствующее или некорректное
значение банка не обнуляет известную сумму; если ни один источник не содержит корректной суммы,
`amount` равен `null` (в админке «—»). Правило округления остаётся ROUND_HALF_UP.
Завершённые записи старых версий не перепроверяются автоматически: для исправления старого нуля
нужна сверка конкретного проекта, типа и ID платежа с банковскими данными. Исторические payload и
ID уже созданных вебхуков при этом автоматически не изменяются.

В создании QR/счёта можно передать `orderId` своего заказа: он сохраняется в журнале и приходит в вебхуках.
Это поле для сопоставления заказов, **не ключ идемпотентности**. Сервер не повторяет банковские запросы создания.
После сетевой ошибки проверьте наличие операции перед повтором. Если Kaspi создал платёж, но запись на диск
не удалась, ответ будет `202` с банковским `Data.QrOperationId` и `tracking.persisted: false`:
сохраните этот ID, устраните ошибку диска и проверьте платёж у администратора; повторять создание нельзя.

### QR

```bash
curl http://127.0.0.1:3000/api/qr/create \
  -H "Authorization: Bearer $SHOP_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"amount":"1500.00","orderId":"order-123"}'
```

| Метод и путь          | Параметры                                                        | Назначение                               |
| --------------------- | ---------------------------------------------------------------- | ---------------------------------------- |
| `POST /api/qr/create` | JSON: `amount`; необязательно `orderId`, `latitude`, `longitude` | Создать QR, автоматически начать polling |
| `GET /api/qr/status`  | Query: `qrOperationId`                                           | Текущий банковский статус своего QR      |

Ответ создания содержит банковский объект `Data`, в том числе `QrOperationId`, `QrToken`, `QrOriginalToken`,
а также `tracking.persisted`. `QrToken` — ссылка `pay.kaspi.kz/pay/` для Kaspi;
`QrOriginalToken` — исходная ссылка `qr.kaspi.kz` для Единого QR.

### Счёт по телефону

| Метод и путь                   | Параметры                                                         | Назначение                        |
| ------------------------------ | ----------------------------------------------------------------- | --------------------------------- |
| `GET /api/invoice/client-info` | Query: `phoneNumber`                                              | Информация о клиенте              |
| `POST /api/invoice/create`     | JSON: `phoneNumber`, `amount`; необязательно `comment`, `orderId` | Выставить счёт, начать polling    |
| `GET /api/invoice/details`     | Query: `operationId`                                              | Статус и детали своего счёта      |
| `POST /api/invoice/cancel`     | JSON: `operationId`                                               | Отменить свой счёт                |
| `POST /api/invoice/history`    | JSON: `{}`; только admin                                          | История счетов выбранного проекта |

В `Data` создания Kaspi возвращает `QrOperationId`, `Amount`, `ClientMobile`, `ReceiptUrl`, `OrderNumber`
в зависимости от ответа банка. Общая структура ответа и банковские коды ошибок сохраняются.

### Журнал проекта

В админке доступен кнопкой «Платежи» в верхней панели или карточке проекта. Это локальный журнал
созданных через сервер операций, включая завершённые, а не полная история счёта в банке.
Администратор передаёт `X-Project-ID`; доступны также отключённые и архивные проекты.
Ответ не кэшируется (`Cache-Control: no-store`) и не содержит банковских учётных данных.
Интерфейс обновляет список каждые 10 секунд; источник статуса — фоновый polling.

```bash
curl 'http://127.0.0.1:3000/api/payments?page=1&pageSize=50&status=all&search=' \
  -H "Authorization: Bearer $SHOP_API_KEY"
```

```json
{
  "payments": [
    {
      "paymentId": "123456",
      "type": "qr",
      "status": "Processed",
      "event": "payment.success",
      "result": "paid",
      "amount": 1500,
      "orderId": "order-123",
      "createdAt": 1794230000000
    }
  ],
  "total": 1,
  "page": 1,
  "pageSize": 50,
  "summary": { "total": 1, "pending": 0, "paid": 1, "failed": 0, "expired": 0, "review": 0 }
}
```

Параметры запроса:

| Параметр   | По умолчанию | Значение                                                                                                           |
| ---------- | ------------ | ------------------------------------------------------------------------------------------------------------------ |
| `page`     | `1`          | Положительное целое, до 100000000; за последней страницей возвращается последняя существующая                      |
| `pageSize` | `50`         | Положительное целое до `100`                                                                                       |
| `status`   | `all`        | `all`, `pending`, `paid`, `failed`, `expired`, `review`                                                            |
| `search`   | пусто        | Начало ID платежа или номера заказа, до 120 символов; `%` и `_` — обычные символы, регистр латиницы не учитывается |

Неверные параметры возвращают `400`. Сортировка стабильна: дата создания убывает, затем тип и ID.
`total` — число записей после фильтров; `summary` — счётчики всего выбранного проекта, без фильтров.
Поиск, фильтрация и `LIMIT/OFFSET` выполняются в SQLite. В ответе только одна страница.
`result` — нормализованный результат: отсутствие финального события означает `pending`,
`payment.success/failed/expired` соответствуют `paid/failed/expired`, `payment.lost` — `review`.
Неизвестный банковский статус без финального события остаётся `pending`.

Возвращаются только операции выбранного проекта, включая завершённые. Пока polling не получил финальный статус,
`event` равен `null`. Журнал отражает исходный платёж; текущий статус отмены и суммы возвратов проверяются у Kaspi.

### Возврат

`POST /api/refund/create`: JSON `qrOperationId`, `returnAmount`.
Сервер проверяет принадлежность операции проекту и формат суммы; возможность возврата и доступный остаток
проверяет **Kaspi**, который остаётся источником истины. Результат возвращается в банковском формате.
Администратор может возвращать операции выбранного счёта.

### Банковская история — только администратор

Передавайте `X-Project-ID` с ID счёта, для которого запрашивается история.

| Метод и путь                   | JSON                                                                                                    |
| ------------------------------ | ------------------------------------------------------------------------------------------------------- |
| `POST /api/history/operations` | `endDate` (`YYYY-MM-DD`); необязательно `lastTransactionDate`, `statementPeriodCode` (по умолчанию `0`) |
| `POST /api/history/details`    | `id`; необязательно `operationMethod` (по умолчанию `0`)                                                |

## Webhooks

Вебхуки настраиваются в админке или через `PATCH /api/projects/:id`. Пример тела запроса:

```json
{
  "webhooks": [
    {
      "url": "https://shop.example.com/api/kaspi/webhook",
      "events": ["payment.success", "payment.failed", "payment.expired", "payment.lost"]
    }
  ]
}
```

В интерфейсе это поле называется «Секрет проверки уведомлений»: ваш сайт использует его для проверки подлинности сообщения об оплате. Это не пароль Kaspi и не API-ключ проекта. Секрет нового получателя вернётся в `webhookSecrets` только один раз. Сохраните его в интеграции,
принимающей уведомления. В SQLite секрет хранится зашифрованным. Авторизация проекта проверяет хеш API-ключа; отдельная зашифрованная копия позволяет администратору просматривать его повторно.
Сохранение конфигурации не требует SSH или перезапуска. `projects.json` и прежние переменные окружения
используются только при первом импорте в новую базу. URL вебхука задаёт администратор,
пользователь платежа не может подменить адрес уведомления.

Файл `webhooks.json` сохранён только для старых операций. Старые `tracked-payments.json` и `webhook-retries.json`
при первом запуске импортируются с владельцем `__admin__`; они не назначаются произвольному новому проекту.
Новые платежи, созданные администратором, принадлежат проекту, выбранному через `X-Project-ID`.

| Событие           | Значение                                                                              |
| ----------------- | ------------------------------------------------------------------------------------- |
| `payment.success` | Kaspi подтвердил `Processed`                                                          |
| `payment.failed`  | Kaspi сообщил об отказе/отмене                                                        |
| `payment.expired` | Kaspi сообщил об истечении либо после `expireDate` подтвердил промежуточный статус    |
| `payment.lost`    | После 11 неудачных проверок или вытеснения сессии статус неизвестен; требуется сверка |

Неизвестный банковский статус не считается отказом и продолжает опрашиваться. `payment.lost` не означает,
что деньги не поступили. Polling выполняется каждые 3 секунды без перекрытия циклов.

Пример HTTP POST payload:

```json
{
  "event": "payment.success",
  "projectId": "shop",
  "paymentId": "123456",
  "type": "qr",
  "status": "Processed",
  "statusDesc": "",
  "amount": 1500,
  "orderId": "order-123",
  "qrToken": "https://qr.kaspi.kz/...",
  "receiptUrl": null,
  "orderNumber": null,
  "data": { "Status": "Processed" },
  "timestamp": "2026-11-09T12:00:00.000Z"
}
```

Подпись: `X-Webhook-Signature: sha256=<hex HMAC-SHA256>` от **исходных байтов тела запроса** с секретом вебхука.
Проверяйте её до разбора/обработки тела. `X-Webhook-ID` остаётся одинаковым при повторной доставке:
получатель должен обрабатывать этот идентификатор идемпотентно.

HTTP 2xx подтверждает доставку. Сетевые ошибки, таймаут 10 секунд и HTTP 4xx/5xx вызывают повтор:
всего 3 попытки с задержками 5 и 30 секунд. После последней ошибки автоматические повторы
останавливаются, доставка остаётся в SQLite со статусом `failed`, а ошибка — в журнале и логах. После рестарта возможна повторная доставка уже полученного события.
Перенаправления не выполняются. Финальный статус и очередь сохраняются одной транзакцией в `DATA_DIR/projects.sqlite`.
JSON-журналы автоматически импортируются один раз; после миграции не читаются и не обновляются.
Секреты подписей в очереди не сохраняются: берутся из SQLite, включая после ротации.
Удаление URL или подписки отменяет ещё не отправленные доставки этому получателю. Архивирование проекта сохраняет получателей для уже созданных платежей.

## Журнал доставки вебхуков — только администратор

В админке кнопка «Доставка вебхуков» открывает отдельный журнал выбранного проекта, включая архивные.
Статус оплаты и статус доставки независимы: `delivered` означает HTTP 2xx от сайта, но не доказывает,
что сайт обновил заказ или выполнил свою бизнес-логику. Тело ответа сайта и секрет подписи не сохраняются
в журнале и не возвращаются его API. Изменения не затрагивают формат существующих уведомлений.

Все маршруты требуют полного доступа администратора и `X-Project-ID`; ключам проектов доступ запрещён.
Для POST с браузерной cookie требуется CSRF-токен. Ответы не кэшируются.

| Метод | Путь                                | Результат                                                           |
| ----- | ----------------------------------- | ------------------------------------------------------------------- |
| GET   | `/api/webhook-deliveries`           | `{deliveries, total, page, pageSize, summary}`                      |
| GET   | `/api/webhook-deliveries/:id`       | `{delivery, attempts}` — сведения о доставке и история HTTP-попыток |
| POST  | `/api/webhook-deliveries/:id/retry` | HTTP 202 `{delivery}` — повтор поставлен в очередь                  |

Список принимает `page` (по умолчанию 1), `pageSize` (50, максимум 100), `status` (по умолчанию `all`),
`search` (до 120 символов, префикс ID платежа или заказа, символы `%` и `_` ищутся буквально).
Фильтры и пагинация выполняются на сервере; summary содержит счётчики проекта без фильтров.
Список сортируется по дате создания и ID, по убыванию. Чужой или неизвестный ID доставки возвращает 404.

| Статус      | Значение                                                             |
| ----------- | -------------------------------------------------------------------- |
| `queued`    | Ожидает первой отправки или ручного повтора                          |
| `sending`   | HTTP-запрос выполняется                                              |
| `retrying`  | Предыдущая попытка неуспешна, назначен автоматический повтор         |
| `delivered` | Получен HTTP 2xx                                                     |
| `failed`    | Исчерпаны три попытки, требуется действие администратора             |
| `cancelled` | Получатель удалён, его URL изменён или подписка на событие отключена |

Запись содержит ID доставки/платежа/заказа, событие, URL, статус, общее количество попыток,
последние HTTP-код и ошибку, даты создания/обновления/успеха/следующего повтора, `canRetry` и
`retryDisabledReason`. История содержит номер, начало/конец, HTTP-код, ошибку, длительность и
результат каждой новой попытки. После перезапуска незавершённая попытка отмечается `interrupted`:
запрос мог дойти до сайта, поэтому его результат неизвестен; повтор использует прежний ID.

Ручной повтор доступен для `delivered`, `failed`, `cancelled`, если сохранились тот же получатель,
URL и подписка на событие. Для ожидающей или выполняющейся доставки возвращается 409.
Повтор сохраняет **исходные payload и X-Webhook-ID**, историю и общий счётчик; начинает новый цикл
до трёх попыток с текущим секретом настроенного получателя. Повтор не создаёт новый платёж.
Получатель обязан идемпотентно обрабатывать одинаковый X-Webhook-ID. Удалённая и созданная заново
подписка с другим ID не подменяет прежнего получателя.

Миграция очереди SQLite выполняется автоматически и транзакционно. Существующие ожидающие доставки
сохраняют ID, владельца, payload, номер попытки и дату следующего отправления. Их прошедшие попытки
учитываются в общем счётчике, но старые HTTP-коды и ошибки восстановить нельзя. Ранее удалённые
успешные/исчерпанные доставки не восстанавливаются. Новые записи и история попыток сохраняются в
`webhook_deliveries` и `webhook_delivery_attempts` внутри того же `projects.sqlite` и Docker volume.

Перед обновлением сохраните резервную копию базы. Понижение версии на обновлённой базе не поддерживается:
старый обработчик не учитывает статусы журнала и может повторно отправлять завершённые доставки.
Для возврата к старому образу нужен отдельный план обратной миграции данных.
